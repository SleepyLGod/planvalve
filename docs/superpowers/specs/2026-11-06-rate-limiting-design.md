# 调度需求与选型依据

2026-11-06。状态：已按确认的需求完成离线实现与验收；真实限流和长期运行未验证。具体选型与契约见[实现方案](../plans/2026-11-06-bounded-scheduling.md)。此前“固定单并发、不新增依赖”的方案已撤回，不能当作已确认的实现约束。

## 先确定要解决的问题

通用 API 客户端可能同时提交一批请求。网关需要限制自己的发送行为，避免无界排队、瞬时突发和失控消耗，并明确交代每条请求是在等待、已发送、已完成还是失败。并发控制不等于 CPU 并行，也不能替代请求速率、token 限制或累计预算。

目标是一个本机、单进程、单上游的调度器：默认保守，用户可以明确提高并发和调整节奏；底层尽量使用轻量成熟库。LOTUS／LiteLLM 是客户端案例，不进入核心设计。

实施前已有：串行 FIFO、发送间隔、队列容量、排队期限、单次执行超时、运行请求／已观测 token 预算、SQLite 和中英文监控。当时的缺口是可配置并发、可选本地 RPM、临时冷却后的继续派发，以及多请求同时执行时的状态与预算正确性；现已实现，具体证据见[验收记录](../../offline-verification.md)。下面保留需求与选型时的分析，不把后续少量真实请求当作全面验收。

## 需求基线

| 能力 | 对用户的行为与默认值 |
| --- | --- |
| 并发上限 | 可配置正整数；默认 1。限制未结束的模型请求，不自行调高或调低。 |
| 发送节奏 | 保留最短启动间隔；真实模式默认 3 秒。并发增加不取消节奏限制。 |
| 本地 RPM | 用户已选择加入；默认不设，由用户填写。限制经过本网关的发送，不推断账号额度。 |
| 排队 | 有容量、有等待期限，可取消；同优先级按 FIFO 开始处理，完成顺序允许不同。 |
| 执行期限 | 保留单次绝对超时，必须作用到底层传输，不能只结束外层等待后把请求留在后台。 |
| 运行预算 | 实际发送前统一检查并扣计请求数，不能因并发超发；token 按已观测 usage 停止后续派发。 |
| 上游反馈 | 有可靠等待提示的明确临时限流／过载，推迟尚未发送的任务，到期重新检查后继续。 |
| 失败策略 | 失败请求不重新入队；SDK 与网关自动重试均为 0。不自动切换账号、上游或计费方式。 |
| 监控 | 显示配置上限、实际在途、等待数、等待原因／倒计时、暂停原因及用量完整性。 |

以下是架构建议，不冒充用户已选择的细节：本地 RPM 的验收口径使用任意连续 60 秒的实际发送次数，不采用会在分钟交界突发的自然分钟计数；允许实现比该上限更平滑，但不得提前消费下一分钟额度。配置名拟为 `concurrency` 与 `maxRequestsPerMinute`，后者默认 `null`。已有配置缺少新字段时仍按单并发、无本地 RPM 上限解释。

### 必须说明白的边界

- token 停止阈值不是严格费用上限：阈值达到时，已经发出的多条请求仍可能继续产生 usage。订阅通道目前不支持 `max_output_tokens`，不能声称预留一个准确的输出上界。
- 本轮不实现靠事后 usage 假装精准的 TPM 限制。保留 token 统计／预算，利用上游明确的 token 限制反馈；预测 TPM 如有需求须另定计数与预留语义。
- 并发、间隔、RPM、预算和上游冷却同时约束实际发送。授权等待不能导致随后几条请求挤在一起发出。库在“任务开始”计数，不一定等于网络实际发送，方案必须处理这个差别。
- 已发出的请求不能撤回或当作从未发生；暂停只阻止新发送，仍须收集在途请求的结果和 usage。成功响应不得解除其他请求引发的暂停，也不得缩短已有冷却。
- 排队容量和监控不能只相信库的 pending 数：授权准备、节奏等待、底层实际在途须定义清楚，避免显示“并发已经释放”但传输仍在执行。
- 官方限制可能与其他程序共享；上游返回的剩余值只是最后观察，不是账号余额。重启不代表官方额度恢复。

## 借鉴 sub2api 的什么

相同点是统一 API 入口、并发槽位、等待队列、上游冷却及用量记录。源码将这些职责拆开，适合作为设计参考：

- [并发服务](https://github.com/Wei-Shaw/sub2api/blob/main/backend/internal/service/concurrency_service.go)：申请槽位并在结束后释放；执行数与等待数分开。
- [槽位存储](https://github.com/Wei-Shaw/sub2api/blob/main/backend/internal/repository/concurrency_cache.go)：Redis 原子操作解决跨实例并发。本机单进程不需要照搬 Redis、租约和过期槽位系统。
- [RPM 计数](https://github.com/Wei-Shaw/sub2api/blob/main/backend/internal/repository/rpm_cache.go)：请求速率与并发分开，但该实现采用自然分钟计数，不能据此声称任意连续 60 秒均不突发。
- [模型冷却](https://github.com/Wei-Shaw/sub2api/blob/main/backend/internal/service/model_rate_limit.go)：冷却是独立状态，可查询剩余时间。

参考职责与失败场景，不复制源码。多租户、账号池、跨实例协调、粘性会话、自动切号和重试不是我们已确定的需求。

## 成熟库对照：先看语义，再选参数

下表记录 2026-11-06 实施前查询 npm 注册表及发布包源码的选型比较；项目最终采用 p-queue，实施与验收结果见实现方案及验收记录。

| 候选 | 已确认的适用能力 | 必须补齐／验证的差别 |
| --- | --- | --- |
| `p-queue@10.0.0` | MIT、无运行依赖、约 101 KiB 解包；原生 ESM、类型声明；并发、FIFO、取消、暂停及滚动窗口限速。2026-10-12 发布，适配本项目 Node 26。 | 没有独立 `minTime` 参数；窗口用系统时钟；限速计算任务开始，非必然的实际发送；运行中取消／超时会释放槽位，底层仍须响应取消。 |
| `bottleneck@2.19.5` | MIT、无运行依赖、约 614 KiB 解包；直接提供 `maxConcurrent`、`minTime`、队列容量及 reservoir。 | 最新 npm 版发布于 2019-08-03；reservoir 定期刷新不是严格滚动 RPM；取消、暂停恢复和底层超时须适配；其本地调度也使用系统时钟。 |
| 继续扩展自研队列 | 不增加依赖，旧行为可控。 | 要自行维护多并发、取消、结束与唤醒边界；与用户优先复用成熟库的方向不符。 |

来源：[p-queue 发布版文档](https://github.com/sindresorhus/p-queue/blob/v10.0.0/readme.md)、[p-queue npm 元数据](https://registry.npmjs.org/p-queue)、[Bottleneck 文档](https://github.com/SGrondin/bottleneck/blob/v2.19.5/README.md)、[Bottleneck npm 元数据](https://registry.npmjs.org/bottleneck)。大小为包总解包大小，不是内存占用或 bundle 大小。

建议采用“成熟库负责通用任务队列，一层小适配负责网关发送约束”的方向，优先评估 p-queue，而不是因为 Bottleneck 参数更像需求就直接拍板。最终方案须交代最短间隔与实际发送 RPM 如何同时成立、取消如何真正终止传输，并证明没有重复实现两套任务队列。不能通过改全局时钟、改第三方包源码或引入 Redis 来迁就库。

## 实施前确认的问题（现已完成回归修复）

1. `officialUpstream` 的当前记录与发送回调是共享变量。改为每条请求独立持有；不能只改并发数字，否则可能串写状态、usage 和错误。
2. 请求预算当前在执行开头检查，发送回调才增加尝试数。多请求授权等待时可能同时通过检查；须在实际发送前做一次不可交错的检查、持久化与计数。
3. 授权刷新已有共享 Promise，但使用首个调用者的取消信号；并发下应区分共享刷新生命周期和单个请求等待期限，避免一个任务到期影响其他任务。仍只允许一个刷新拥有者。
4. 收到临时限制后只推迟未发送工作；已有多个反馈时采用最晚的可靠期限。订阅用量超限、余额／账单、身份／权限和存储失败保持暂停，等待头不能覆盖这些原因。
5. 所有退出路径均结算自己的请求：完整结果、断流、失败、超时、取消及缺失 usage 分开；不伪造成功，不因库释放槽位而漏记在途调用。

## 验收标准与工作顺序

先用本需求基线写出具体实现方案，再实施；不把依赖安装或未验证的代码称为已完成选型。

- 对固定发布版验证核心调度契约：64 个客户端、并发 1／2／4，不超过上限，确实能有多条在途；发送间隔与滚动 RPM 同时成立。
- 故意让授权准备变慢、改变系统时间、打乱响应完成顺序；发送不得扎堆，usage 与 metadata 不串台，请求预算不超发。
- 覆盖临时限制有／无有效提示、额度／账单／权限错误、并发反馈、取消、排队到期、执行超时、关闭和存储失败。失败请求的上游发送次数必须为 1。
- 验证预算触发时在途结果正常收尾；缓存／推理细分保留未知语义；持续刷新监控不改变预算或触发模型。
- 类型检查、构建、完整离线测试、普通 SDK 和独立 LiteLLM 验收分别报告；依赖安装如需联网仅获取项目依赖，运行验收拦截外部连接。

实施阶段仅在本项目内，不修改其他仓库、日常 Codex 配置或已有私人配置；当时不登录、不发真实模型请求、不提交或推送。后续有界真实验收和私有开发分支保存另行获得授权，不改变默认离线行为。跨机器、后台守护和自适应并发均未实施。

## 官方依据

- [API 限流与等待提示](https://developers.openai.com/api/docs/guides/rate-limits)：不同维度的限制、实际计数与事后 usage 的差别，以及临时错误与额度／账单错误的区分。
- [订阅错误处理](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery)：订阅用量超限暂停新请求，不从错误码自行推断恢复时间。
- [订阅接口限制](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)：当前不支持输出 token 上限等字段。

默认单并发和 3 秒间隔只是本地策略，不是官方安全阈值。本工具只能约束经过自身的流量，不保证避免限流或账号封控。
